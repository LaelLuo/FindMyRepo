# 按意图发现 GitHub 仓库

你要解决的问题：用户想开发某功能，想知道 GitHub 上有没有现成库/实现。难点是用户描述用词和仓库作者用词常常不一样（用户说「统一接口」，仓库写 "programming interface for agent harnesses"），单次关键词搜索会漏掉真正的项目。

## 核心方法

**让搜索结果教你下一轮用什么词。** 这是覆盖小众仓库的关键。不要在一开始就把用户的话当成唯一关键词。

## 工具

单轮搜索命令（工作目录 `E:/Projects/Playground/projects/gh-repo-finder-app`）：

```bash
python -m finder search "<查询>" --limit 20 --json
```

- 查询词支持 GitHub 搜索语法，也可直接放自然语言片段。
- `--json` 输出 `full_name`、`description`、`stars`、`url` 数组，并在 stderr 用 `# source=...` 标注是否来自缓存及历史术语提示；去掉 `--json` 是人类可读列表，首行直接标 `[实时]` / `[来自缓存]`。
- `--refresh` 忽略缓存强制重搜；`cache path|clear|export` 查看/清空/导出缓存。
- 结果自动存到本机缓存（用户配置目录的 SQLite），同查询下次直接复用；新查询的文字输出里会显示「历史术语提示」，这些是以前摸到的线索，可作为新一轮的候选词，但**不是结果**。
- 种子查询在自然语言里混入最核心的 2–4 个英文词效果最好（如 `coding agent orchestration tool`）。
- 需要 `gh` 已登录（`gh auth login`）；限流约 30 次/分钟，轮数控制在 3–5 轮。

## 迭代流程

1. **起轮**：把用户意图拆成宽泛的英文关键词（含 1 个同义/上位词），跑 `python -m finder search "<查询>" --limit 20 --json`。先看输出里有没有「历史术语提示」——有就把它们当作候选词，但仍要自己判断哪些与当前意图相关，不要盲信。若提示显示缓存可能过期，用 `--refresh` 重搜。
2. **读结果**：逐条看 `description`，找出你事先没想到、但和意图相关的**术语或项目类型词**。例：用户没提 "harnesses"，结果里出现 "the harnesses that orchestrate them" → "harnesses" 就是新线索。
3. **下一轮**：用新术语构造查询（可和核心词组合），再搜。例：`agent harnesses interface` → 找到 `botiverse/oar`。
4. **重复** 2–3 步，直到：
   - 找到明显匹配的项目；或
   - 连续一轮没有新术语，说明词已收敛，停止。
5. **沉淀术语**：把这次迭代发现的新术语记回缓存，供下次搜索借鉴：
   `python -m finder hint "<最初的查询>" <术语1> <术语2> ...`
   只记你确实从结果里学到的词，不要记用户一开始就说出来的词。
6. **输出**：给用户相关项目清单，每项写清名称、描述、链接，以及**是哪一轮、靠哪个术语命中的**。这能让用户判断相关性。

## 判断标准

- 相关：项目描述直接覆盖用户要做的核心功能，或是一个能直接用的库/框架。
- 弱相关但有用：awesome 列表、竞品、相邻方案——可以单独列「参考」，不要混进主结果。
- 无关：只有字面词重合，功能不对，丢弃。

## 已知边界（对用户诚实）

这套方法覆盖面高但非穷尽：如果某仓库完全不含任何被搜到的词，就找不到。它不建全站索引，也不保证按时效排序。如果用户需要「穷尽全站」，说明这超出当前能力，不要假装找到的就是全部。

## 错误

- `未找到 gh 命令行` → 提示安装 GitHub CLI。
- `gh 未登录` → 提示 `gh auth login`。
- `限流` → 提示稍后重试，减少轮数。
- 查询为空 → 重新构造非空查询。
